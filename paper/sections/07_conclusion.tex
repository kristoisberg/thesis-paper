\section{Conclusion}\label{sec:conclusion}

% Source: chapters/09_summary.tex, study summary and calibrated takeaway.

This thesis developed an automated, LLM-powered static analysis tool to detect SQL antipatterns in Java source code that uses jOOQ and analysed the distribution of its flags in an identified open-source corpus.

The study began with mining \num{602} open-source jOOQ projects. A size-stratified sample of 61 projects was manually annotated, resulting in \num{1562} reference occurrences across 19 SQL antipatterns. Following the analysis support rule, 12 antipatterns were excluded, leaving seven for the subsequent stages. This dataset enabled an evaluation of four LLMs across multiple prompting strategies. For Claude Opus 4.5, the reasoning-oriented prompts reported F1-score \num{0.90} rather than the Zero-Shot value of \num{0.88}, with higher observed costs and runtimes. We selected the simpler Zero-Shot configuration with reasoning disabled. Against the original single-annotator reference spans, one selected run achieved micro precision of \num{0.858}, recall of \num{0.880}, and F1-score of \num{0.869}; per-class F1-scores ranged from \num{0.48} to \num{0.97}.

Deploying the finalised tool across the \num{602}-project corpus produced \num{15931} flags across seven classes. Implicit Columns and ID Required had at least one flag in \qty{89}{\percent} and \qty{87}{\percent} of repositories. Among Implicit Columns flags, \qty{71.7}{\percent} matched the two largest post hoc source-fragment categories; among Poor Man's Search Engine flags, \qty{46.8}{\percent} matched fragments containing \texttt{like(}. These are unnormalised detector-output distributions rather than estimates of antipattern prevalence.

The primary occurrence-level agreement bounds how the corpus detector outputs may be interpreted. Independent reference annotation, repeated detector runs, and exposure-normalised corpus measures are needed before making stronger claims about prevalence or API-associated risk.
