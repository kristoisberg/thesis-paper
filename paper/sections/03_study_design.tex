\section{Study Design}\label{sec:studyDesign}

\subsection{Study overview}

The study connects an occurrence-level detector evaluation to a repository-level description of detector output. We first identified a target population of open-source Java repositories that use jOOQ and retain generated schema classes. We then annotated a size-stratified sample, partitioned its projects into training, validation, and test sets, selected one detector configuration on the validation set, and evaluated one run on the held-out test set. Finally, we applied the selected detector to the full identified corpus and coded recurring API patterns among two classes of flags. This sequence keeps detector selection separate from held-out evaluation and makes the unit of each reported result explicit.

The design uses three empirical units. Reference and predicted occurrences are class-labelled line spans within files. The held-out evaluation matches these occurrences one to one. The corpus analysis counts detector flags and repositories with at least one flag. These units support the three research questions without treating unverified corpus flags as reference annotations.

\subsection{Repository mining and target population}\label{sec:mining}

We defined the target population as the repositories identified by our dated GitHub search and subsequent filters. It does not represent every jOOQ project on GitHub or in other hosting services. On 10 January 2026, we queried the GitHub Code Search API \nobreakcite{githubSearchApi} for jOOQ dependency declarations in Maven and Gradle manifest files \nobreakcite{maven2026homepage,gradle2026homepage}. Manifest queries reduced duplication within the API's limit of \num{1000} results per query. The exact search terms are available in the Online Resources.

The search returned \num{3829} repositories. We retained \num{802} that stored jOOQ-generated classes in version control, because these classes expose schema information without rebuilding each project \nobreakcite{jooq2025code}. Requiring at least one non-generated Java file that referenced jOOQ or a generated class left \num{645} repositories. We then reviewed duplicate candidates identified from repository file trees with Google Gemini 3 Pro Preview \nobreakcite{gemini3ProPreview}. Human review removed \num{42} duplicates or unsuitable copies, yielding the preliminary \num{603}-repository corpus used for sampling. A further duplicate found before corpus execution reduced the final analysis corpus to \num{602} repositories. Figure~\ref{fig:dataFunnel} records these successive boundaries.

This mining procedure establishes the population to which the corpus counts refer. The next step defines which files and antipattern occurrences the study measures within that population.

\subsection{Operational scope}\label{sec:antipatternSelection}

We studied static evidence available in Java source code. A file was relevant when it was generated by jOOQ or referred to jOOQ or a generated class. A manually maintained path list excluded generated records and plain data objects, as well as classes generated from external system schemas or extension-managed tables. We did not build or execute the repositories because their Java versions, build systems, private dependencies, and database configurations varied. The analysis therefore concerns source-represented schema and query patterns.

The annotation codebook began with 19 antipatterns from \nobreaktextcite{karwin2023sql}. We excluded concepts that require runtime performance evidence, organisational practice, or framework-level exception behaviour. We restricted Fear of the Unknown to database-design occurrences and null-unsafe query conditions whose values were visible in the analysed source. We extended Implicit Columns to blind projections expressed through jOOQ convenience methods \nobreakcite{jooq2025select}. The full codebook, exclusions, and decision trees are available in the Online Resources.

Downstream experiments used the seven classes defined in Table~\ref{tab:evaluatedAntipatterns}. This restriction followed the support rule described below and kept the detector evaluation within classes represented across several sampled projects.

\subsection{Sampling, reference annotation, and reliability}\label{sec:referenceAnnotations}

The reference sample came from the preliminary \num{603}-repository corpus. We counted relevant files per repository and used two recursive mean splits to form size strata. Breakpoints of \num{31} and \num{94} relevant files classified \num{467} repositories as small, \num{100} as medium, and \num{36} as large. Sampling \qty{10}{\percent} from each stratum with pseudorandom seed \num{123456} selected \num{47}, \num{10}, and \num{4} repositories, respectively. The resulting \num{61}-repository sample preserves representation from each observed size stratum without claiming statistical representativeness beyond the identified corpus.\label{sec:sampleGeneration}

One annotator with prior jOOQ and SQL-antipattern experience reviewed the sampled source code. Each record contained the antipattern class, repository, relative file path, inclusive start and end lines, and a short note. The annotator developed decision flowcharts during the review and revisited earlier files whenever a new variant or edge case changed a rule. This process produced \num{1562} occurrences across the 19 initially included classes. The seven classes retained for detector evaluation account for \num{1436} of those occurrences.

We measured temporal repeatability after a 30-day washout period. A seeded sample contained \qty{10}{\percent} of files with at least one annotation and an equal number of files without annotations, for \num{128} files in total. The original and repeated passes contained \num{158} and \num{149} events and matched exactly on class and span for \num{142}. Treating the original pass as reference gives precision \num{0.953}, recall \num{0.899}, and F1 \num{0.925}. These values measure one annotator's repeatability. Annotation correctness remains unmeasured because no independent annotation and adjudication were available.

\subsection{Project-disjoint partitioning}\label{sec:dataSplit}

We assigned complete repositories to training, validation, and test sets to prevent files from one project appearing in more than one stage. Training data supported prompt development and Few-Shot examples. Validation data supported model and prompting-strategy selection. The test set remained held out until the selected detector was evaluated.

Class and split selection used the complete \num{61}-repository annotation set. We retained classes with at least \num{25} occurrences in at least three projects, leaving seven of the 19 annotated classes. We then evaluated all \num{1000000} integer seeds from \num{0} through \num{999999}. Each seed assigned \num{21}, \num{20}, and \num{20} projects to the training, validation, and test sets. The objective minimised the sum of squared coefficients of variation in per-class occurrence counts across the three splits. Seed \num{767573} achieved the lowest score, \num{0.52}. This label-informed procedure balanced occurrence counts, while Table~\ref{tab:trainingTestValidationSplit} shows that project support remained sparse for several classes.

The support rule and seed search were data-dependent design choices. Holding out whole projects still prevents direct file-level overlap between development and test data, which is the separation required for the detector evaluation.

\subsection{Detector configuration and execution}\label{sec:experimentsQuantitative}

We designed four universal prompt configurations on the training set. Zero-Shot and Few-Shot followed established prompting designs \nobreakcite{DBLP:journals/csur/LiuYFJHN23,DBLP:conf/nips/BrownMRSKDNSSAA20}. Chain-of-Thought and Tree-of-Thought-inspired prompts elicited explicit intermediate analysis \nobreakcite{DBLP:conf/nips/KojimaGRMI22,DBLP:conf/nips/Wei0SBIXCLZ22,tree-of-thought-prompting,DBLP:conf/nips/YaoYZS00N23}. Each configuration had one prompt for query code and one for generated schema code. The schema prompt also received the closest generated key-definition class to support Keyless Entry decisions. We removed leading and trailing whitespace, prefixed source lines with their original line numbers, and required structured class, span, code-fragment, and explanation fields. The Online Resources provide the exact prompts and localisation rules.\label{sec:prompts}

We compared four models and the four prompting configurations on the \num{20}-repository validation set, which contained \num{823} relevant files. The models were OpenAI GPT-5.2 \nobreakcite{gpt52}, Z.ai GLM-5 \nobreakcite{DBLP:journals/corr/abs-2602-15763}, Anthropic Claude Opus 4.5 \nobreakcite{opus45Card}, and OpenAI gpt-oss-120B \nobreakcite{DBLP:journals/corr/abs-2508-10925}. Validation requests used the OpenAI Python SDK \nobreakcite{openAiPython2026GitHub} through OpenRouter \nobreakcite{openRouter2026homepage}, with automatic provider fallbacks disabled. GPT-5.2 used xhigh reasoning and did not accept a temperature parameter. GLM-5 used temperature \num{0.0} without a configurable reasoning level; Claude Opus 4.5 used temperature \num{0.0} with reasoning disabled; and gpt-oss-120B used temperature \num{1.0} with high reasoning. Each model-prompt pair was run once, and we selected the final configuration from the observed agreement, cost, and runtime on this validation partition. Results reports the comparison and selection outcome; per-class and diagnostic outputs are available in the Online Resources.\label{sec:models}

The final detector recursively selected relevant Java files, attached key-definition context where available, sent one structured request per file, and retained each returned class-labelled span. The released detector commit fixes file discovery, context attachment, prompt-size truncation, structured-output validation, retry handling, and failed-file reporting. We executed one primary run on the \num{20} held-out projects, covering \num{502} relevant files. The run cost \usd{14.34}, took \num{386} seconds, and returned \num{536} predictions. The same selected configuration then produced the corpus flags used for RQ2 and RQ3.

\subsection{Localisation evaluation and error analysis}

The primary evaluation compares the \num{536} held-out predictions with \num{523} original single-annotator reference spans. A candidate match must share repository, file, and class. For predicted span $S_p$ and reference span $S_r$, we compute line-level intersection over union:
\begin{equation}
    \operatorname{IoU}(S_p,S_r)=\frac{|S_p\cap S_r|}{|S_p\cup S_r|}.
\end{equation}
At the primary threshold of \num{0.50}, maximum-cardinality bipartite matching assigns each prediction and reference to at most one pair. Candidate lists are ordered by descending IoU, predicted span, and source order for deterministic tie handling. Matched pairs are true positives, unmatched predictions are false positives, and unmatched references are false negatives. One reversed Keyless Entry reference span was invalid and remained unmatched.

We calculate precision, recall, and F1 from these event counts for each class. Micro averages pool events across classes, macro averages weight classes equally, and reference-support-weighted averages use each class's reference count. True negatives are undefined for occurrence localisation, so these counts are event matches rather than confusion matrices.

Two robustness procedures test the primary result. First, we repeat the one-to-one matching at IoU thresholds \num{0.25}, \num{0.75}, and \num{1.00}. Second, a project-cluster bootstrap resamples all \num{20} test projects with replacement for \num{10000} iterations using seed \num{20260827}. Each draw retains every reference and prediction from a sampled project. The percentile ranges measure sensitivity to project composition within the selected split. They do not measure population sampling uncertainty or detector run-to-run variation.

We manually reviewed unmatched references and predictions to classify recurring semantic and localisation errors. This detector-informed review also produced a revised set of \num{563} reference events. The original annotations remain the primary reference because detector disagreements determined which records received further review and occurrences missed by both passes could remain undiscovered. Results against the revised records are therefore reported as an optimistic sensitivity analysis. This protocol keeps the primary agreement claim tied to the original reference process while using the error review to show its likely direction of bias.

\subsection{Corpus measures and API-pattern coding}\label{sec:corpusMeasures}

One corpus run applied the selected configuration to all \num{602} repositories, including the \num{61} sampled repositories, and covered \num{17450} relevant files. It produced \num{15931} positive flags. For each class, we count flags, repositories with at least one flag, flags per repository across the full corpus, and flags per flagged repository. These unnormalised quantities describe detector output in the identified corpus. They do not estimate true antipattern prevalence because the corpus lacks independent reference annotation, class-specific error correction, repository-size adjustment, and an API-exposure denominator.

For Implicit Columns and Poor Man's Search Engine, we assigned one post hoc API or source-pattern category to each detector flag. The coding procedure applies a fixed, precedence-ordered list of string and regular-expression matches to the code fragment returned by the detector. The first matching pattern determines the category. Flags with no matching pattern remain in an other or uncategorised group. The procedure does not resolve source-level call targets, so the categories describe fragments associated with flags rather than API-specific risk. The Online Resources provide the ordered patterns.

This analysis frame connects the occurrence-level evaluation to the repository results: RQ1 establishes agreement on held-out projects, RQ2 describes all corpus flags, and RQ3 groups recurring manifestations within two flag classes.

\subsection{Reproducibility and AI-use disclosure}

The surviving study artefacts are frozen in the public \texttt{masters-thesis} repository at commit \href{https://github.com/kristoisberg/masters-thesis/tree/d9b35e398a6deb544f913bdbc0b211ab38474a44}{\texttt{d9b35e3}}. They include the \num{523} original test reference spans, the executed notebook containing all \num{536} held-out predictions, the \num{15931} positive corpus flags, prompts, annotation materials, and analysis scripts. The original data processing and evaluations used Jupyter notebooks \nobreakcite{jupyterHomepage}. The IoU sensitivity and project-cluster bootstrap reconstruction use \path{analysis/localisation_robustness.py}.

Detector source is frozen separately at commit \href{https://github.com/kristoisberg/jooq-antipattern-detector/tree/cf82fe56acb728f076df67279ff4a78a138996f3}{\texttt{cf82fe5}}. These commits identify the surviving materials. The original runs did not record the analysed source-repository revisions, detector revision, raw API responses, request identifiers and complete request metadata, retry histories, complete provider metadata, or the full \num{17450}-file corpus frame including files without flags. A future reproduction can inspect the preserved outputs and rerun the released pipeline, while exact replay of the original requests and repository states is unavailable.

We used AI tools in four roles. For research support, Google Gemini 3 Pro Preview screened repository file trees for duplicate candidates, and we manually reviewed every proposed omission. Google NotebookLM \nobreakcite{notebookLm2026homepage} assisted synthesis of the full SQL-antipattern catalogue supplied in the Online Resources. For coding, OpenAI Codex with GPT-5.4 \nobreakcite{openAiCodex2026GitHub,gpt54} assisted implementation of the detector under human-defined requirements, review, and acceptance. For drafting, Google Gemini 3.1 Pro Preview \nobreakcite{gemini31ProPreview} and Codex generated or restructured portions of the thesis and article. For language editing, Gemini 3.1 Pro Preview, Gemini 3 Flash Preview \nobreakcite{gemini3FlashPreview}, and Codex suggested revisions. The authors checked the generated research decisions, code, prose, and edits and retain responsibility for the work.
