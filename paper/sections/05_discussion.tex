\section{Discussion}\label{sec:discussion}

The detector's flags could help developers select code for manual inspection. This would involve checking whether the flagged code meets the antipattern definition and whether the application's requirements justify a change. The study did not evaluate a developer review workflow. We first discuss how developers could use the findings to inspect flagged code. We then outline an independent audit in which annotators examine flagged and unflagged code to measure detection errors.

\subsection{Interpreting flags by antipattern class}

Different antipattern classes require different checks. For Implicit Columns, developers can inspect which columns a query selects and how the application uses its results. For Keyless Entry, they need to decide whether a column represents a relationship that needs a foreign-key constraint. Table~\ref{tab:toolDetections} reports precision of \num{0.984} and \num{0.538}, respectively, against the original reference. This difference also shows why the pooled score provides limited guidance for individual classes.

Audit-log tables illustrate why this decision needs application context. They accounted for half of Keyless Entry's apparent false positives, and the prompt did not exempt them. Before changing the schema, developers would need to assess whether enforcing a relationship suits the table's intended behaviour.

Fear of the Unknown illustrates how incomplete reference annotations affect agreement scores. Of its \num{24} apparent false positives, \num{23} exposed omissions in the original annotations. All \num{17} false negatives involved defaults or sentinel values. The low F1 therefore reflects both detector misses and omissions in the reference annotations. Further validation should check missing-value conventions and the source forms the detector missed.

Poor Man's Search Engine raises a separate question about whether consecutive search expressions should count as separate findings. Grouping them into one predicted span produced most of the class's false negatives. The span may contain the relevant code even when the occurrence counts differ from the reference. During manual inspection, each search expression could be checked separately, with the enclosing query providing context.

\subsection{Interpreting repository-level distributions}

The two dominant classes differ in how broadly and repeatedly they are flagged across the corpus. ID Required flags cover almost half of the generated-schema files and average about one flag per flagged file. Implicit Columns flags cover about one quarter of application/query files and average nearly three flags per flagged file. For ID Required, this suggests checking key designs across many schema definitions. For Implicit Columns, it suggests examining several query expressions together within a smaller share of application files.

For ID Required, developers would need to examine the table definition and its candidate keys. Under the operational definition in Table~\ref{tab:evaluatedAntipatterns}, a primary key named \texttt{id} is sufficient for a flag. File coverage therefore partly reflects how widely this naming choice occurs. Developers would need to assess whether the key design is appropriate and whether a proposed natural or compound key meets the application's requirements. The study reports how widely the detector applies this rule. The consequences of the flagged designs remain unmeasured.

For Implicit Columns, developers could examine repeated expressions together and trace how the application uses the fetched records. They could check whether each expression needs every selected field and which explicit projections would preserve behaviour. Inspecting these expressions together could reveal a shared query-construction convention, which would need confirmation in the source before treating the flags as one refactoring task.

Repository totals need to be interpreted alongside the number of eligible files. A high flag count can reflect a large repository, a high density of flags, or both. An independent audit could use class-specific counts and densities to sample repositories with different distributions of detector output.

\subsection{Priorities for independent corpus validation}

To evaluate detection errors across the corpus, independent annotators should examine code sampled directly from the repositories, including expressions the detector did not flag. Checking flagged expressions against the class definitions can identify false positives. Checking unflagged expressions can reveal missed occurrences. Sampling should span repositories, with adjudication of disputed annotations. An inventory of eligible API uses would supply denominators for comparing how often different source forms are flagged or missed. Together, the inventory and independent annotations could support corpus precision and recall estimates.

Recurring source forms suggest priorities for this audit. Table~\ref{tab:apiManifestations} shows that \texttt{selectFrom} and \texttt{select()} fragments together contain \qty{71.7}{\percent} of Implicit Columns flags. Fragments containing \texttt{like(} account for \qty{46.8}{\percent} of Poor Man's Search Engine flags. These shares describe detector output. Sampling should also cover the remaining categories and forms absent from the flagged fragments to test whether these patterns remain dominant among independently confirmed occurrences.

For Implicit Columns, the held-out errors identify another priority. Fourteen of the \num{17} missed occurrences used an all-column returning clause through \texttt{returning()} or \texttt{returningResult()}. The audit should examine these calls alongside common flagged projection forms. It should resolve their call targets and record whether each expression was flagged. This would test whether similar misses occur in the wider corpus.

The audit of Poor Man's Search Engine should distinguish full-text matching from excluded search forms and record unresolved wildcard behaviour separately. The operational definition conservatively includes unresolved cases, so their uncertainty should remain visible. Annotating consecutive expressions individually, with the enclosing query as context, would also separate judgments about search semantics from disagreements about occurrence grouping.

The independent annotations could also support comparison with a deterministic jOOQ baseline, following established rule-based detection approaches \nobreakcite{DBLP:journals/tse/MohaGDM10}. Candidate rules could detect all-column projections and the primary-key naming condition used for ID Required. Judgments about suitable keys or audit-log relationships would require application context. Comparing the rules and the LLM detector on the same files, class definitions, and occurrence-matching procedure could assess their agreement, cost, and runtime and help identify where model-based interpretation adds value.
