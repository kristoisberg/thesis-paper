\section{Discussion}\label{sec:discussion}

The results suggest that review should depend on the antipattern class and the distribution of its flags. We discuss what reviewers need to check, where to focus their attention, and how an independent audit could test the corpus findings.

\subsection{Interpreting flags by antipattern class}

Different antipattern classes require different review questions. For Implicit Columns, the reviewer can inspect which columns a query selects and how the application uses its results. For Keyless Entry, the reviewer must decide whether a column represents a relationship that needs a foreign-key constraint. Table~\ref{tab:toolDetections} reports precision of \num{0.984} and \num{0.538}, respectively, against the original reference. This difference also shows why the pooled score provides limited guidance for individual classes.

Audit-log tables illustrate why this decision needs application context. They accounted for half of Keyless Entry's apparent false positives, and the prompt did not exempt them. Reviewers must assess whether enforcing a relationship suits the table's intended behaviour before accepting a schema change.

Fear of the Unknown shows why reviewers must also scrutinise the reference annotations. Of its \num{24} apparent false positives, \num{23} exposed omissions in the original annotations. All \num{17} false negatives involved defaults or sentinel values. The low F1 therefore reflects both detector misses and omissions in the reference annotations. Further validation should check missing-value conventions and the source forms the detector missed.

Poor Man's Search Engine raises a separate question about whether consecutive search expressions should count as separate findings. Grouping them into one predicted span produced most of the class's false negatives. A reviewer may see the relevant code in that span, even when the occurrence counts differ from the reference. Presenting each expression as a separate finding, with the enclosing query as context, would align the review interface with the annotation rule.

\subsection{Implications for reviewing repositories}

The distribution of each class's flags suggests where to focus these reviews. ID Required flags cover almost half of the generated-schema files and average about one flag per flagged file. Implicit Columns flags cover about one quarter of application/query files and average nearly three flags per flagged file. ID Required therefore suggests review across many schema definitions. Implicit Columns suggests reviewing several query expressions together within a smaller share of application files.

For ID Required, reviewers need the table definition and its candidate keys. Under the operational definition in Table~\ref{tab:evaluatedAntipatterns}, a primary key named \texttt{id} is sufficient for a flag. File coverage therefore partly reflects how widely this naming choice occurs. Reviewers must assess whether the key design is appropriate and whether a proposed natural or compound key meets the application's requirements. The study reports how widely the detector applies this rule. The consequences of the flagged designs remain unmeasured.

For Implicit Columns, reviewers can examine repeated expressions together and trace how the application uses the fetched records. They can check whether each expression needs every selected field and which explicit projections would preserve behaviour. This review could reveal a shared query-construction convention, which would need confirmation in the source before treating the flags as one refactoring task.

Repository counts and density help choose repositories for inspection. Total counts show how many flags there are to inspect. Density shows how concentrated those flags are relative to the number of eligible files. Pooling classes gives each flag equal weight despite differences in their definitions and review requirements. Class-specific breadth and density can guide inspection. Assessing remediation effort and priority also requires evidence about the validity and consequences of individual findings.

\subsection{Priorities for independent corpus validation}

An independent audit should sample code directly from the repositories, including expressions the detector did not flag. Reviewing flagged expressions can identify false positives. Reviewing unflagged expressions can reveal missed occurrences. Sampling should span repositories, with independent annotations and adjudication of disputed cases. An inventory of eligible API uses would supply denominators for comparing how often different source forms are flagged or missed. Together, the inventory and independent annotations could support corpus precision and recall estimates.

Recurring source forms suggest priorities for this audit. Table~\ref{tab:apiManifestations} shows that \texttt{selectFrom} and \texttt{select()} fragments together contain \qty{71.7}{\percent} of Implicit Columns flags. Fragments containing \texttt{like(} account for \qty{46.8}{\percent} of Poor Man's Search Engine flags. These shares describe detector output. Sampling should also cover the remaining categories and forms absent from the flagged fragments to test whether these patterns remain dominant among independently confirmed occurrences.

For Implicit Columns, the held-out errors identify another priority. Fourteen of the \num{17} missed occurrences used an all-column returning clause through \texttt{returning()} or \texttt{returningResult()}. The audit should examine these calls alongside common flagged projection forms. It should resolve their call targets and record whether each expression was flagged. This would test whether similar misses occur in the wider corpus.

The audit of Poor Man's Search Engine should distinguish full-text matching from excluded search forms and record unresolved wildcard behaviour separately. The operational definition conservatively includes unresolved cases, so their uncertainty should remain visible. Annotating consecutive expressions individually, with the enclosing query as context, would also separate judgments about search semantics from disagreements about occurrence grouping.

The independent annotations could also support comparison with a deterministic jOOQ baseline, following established rule-based detection approaches \nobreakcite{DBLP:journals/tse/MohaGDM10}. Candidate rules could detect all-column projections and the primary-key naming condition used for ID Required. Judgments about suitable keys or audit-log relationships would require application context. Comparing the rules and the LLM detector on the same files, class definitions, and occurrence-matching procedure could assess their agreement, cost, and runtime and help identify where model-based interpretation adds value.
