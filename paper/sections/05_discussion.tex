\section{Discussion}\label{sec:discussion}

\subsection{What occurrence-level validation adds}

Validating individual occurrences reveals information hidden by file classification. As Table~\ref{tab:toolDetections} reports, the held-out run matched \num{460} of \num{523} reference occurrences while producing \num{536} predictions, yielding micro precision \num{0.858}, recall \num{0.880}, and F1-score \num{0.869}. Each match required agreement on the class, the existence of a distinct occurrence, and its source span. The result therefore measures whether the detector identifies the same localised events as the reference process. File-level class presence alone would not supply this evidence.

The pooled score provides only a coarse account of detector behaviour. Per-class F1-scores ranged from \num{0.481} for Fear of the Unknown to \num{0.974} for 31 Flavors. Table~\ref{tab:iouSensitivity} shows a micro-F1 difference of \num{0.010} between the tested span-overlap thresholds. Observed agreement thus varied more across classes than across the tested span boundaries. Corpus flags should be interpreted with class-specific held-out agreement in view.

The disagreement review in Table~\ref{tab:detectionErrors} identifies observable forms of that variation without attributing them to latent model behaviour. Disagreements for Implicit Columns and Poor Man's Search Engine involved local query-method semantics; those for Keyless Entry and Fear of the Unknown involved inferred relationships and missing-value conventions. Other mismatches involved occurrence grouping and span boundaries. These observations locate ambiguities in the supplied source, codebook, and returned spans. They provide no evidence about model reasoning or training data.

The detector-informed reference revision raised micro F1 to \num{0.932}, but the review targeted disagreements already exposed by the detector. The original-reference analysis remains primary, and the revision shows the direction of change under an optimistic detector-informed review. Independent annotation and adjudication would test reference correctness, while repeated detector runs would quantify stochastic stability. Together, those studies would help separate reference disagreement from variation across detector executions.

The same single-run limitation bounds the originally reported Claude Opus 4.5 \nobreakcite{opus45Card} prompt comparison in Table~\ref{tab:configurationSelection}. Zero-Shot and Few-Shot \nobreakcite{DBLP:journals/csur/LiuYFJHN23,DBLP:conf/nips/BrownMRSKDNSSAA20} each had a displayed F1-score of \num{0.88}; Zero-Shot cost \usd{29.97}, compared with \usd{45.00} for Few-Shot. Few-Shot completed in \num{352} seconds, \num{15} seconds faster than Zero-Shot. Chain-of-Thought and Tree-of-Thought-inspired prompting \nobreakcite{DBLP:conf/nips/KojimaGRMI22,DBLP:conf/nips/Wei0SBIXCLZ22,tree-of-thought-prompting,DBLP:conf/nips/YaoYZS00N23} each reported F1 \num{0.90}. Their costs were \usd{40.86} and \usd{81.43}, and their runtimes were \num{956} and \num{4701} seconds, respectively. Zero-Shot was therefore the simplest and lowest-cost of the four reported configurations. The exact outputs underlying these single-run aggregates are unavailable, and run-to-run uncertainty was not measured. These observations motivated the selection without establishing a stable prompt effect or general superiority.

\subsection{Relation to existing detectors}

The main distinction from prior SQL-antipattern detectors is the analysed representation and output unit, summarised in Table~\ref{tab:detectionApproaches}. DbDeo and SQLInspect recover SQL text from host-language source before applying parsing and rules \nobreakcite{sharma2018smelly,nagy2017static,nagy2018sqlinspect}. SQLCheck applies static and dynamic checks to executed queries \nobreakcite{DBLP:conf/sigmod/DintyalaNA20}. Prior LLM work has evaluated smell recognition or classification in PL/SQL source \nobreakcite{de2025effectiveness}. This study instead analyses Java DSL expressions and generated schema classes and returns multiple class-labelled line spans per file.

These measures cannot be ranked directly. They concern SQL extraction quality, statement warnings, source-unit classification, or occurrence-level span agreement. Class definitions also overlap only partly across studies. The held-out F1-scores therefore establish agreement for this study's seven operationalised classes; they do not establish superiority over SQL extraction, rule-based analysis, or PL/SQL classification.

An evaluated deterministic baseline for the same seven-class jOOQ task is absent from the study. A direct comparison would require the same source files, class definitions, reference occurrences, and one-to-one matching rule. Such an experiment could encode syntactically explicit patterns as API or AST rules \nobreakcite{DBLP:journals/tse/MohaGDM10} and reserve contextual cases for an LLM. Its outcome would show whether a deterministic or hybrid design changes occurrence agreement, cost, or runtime under a common task. Architectural differences alone cannot establish an advantage.

\subsection{Implications of recurring source-fragment patterns}

The corpus output contains repeated source-fragment forms that can focus subsequent evaluation. Table~\ref{tab:apiManifestations} shows that fragments matching \texttt{selectFrom} or \texttt{select()} account for \num{5227} of \num{7289} Implicit Columns flags, or \qty{71.7}{\percent}. For Poor Man's Search Engine, \texttt{like(} accounts for \num{273} of \num{583} flags, or \qty{46.8}{\percent}. The reported recurring categories outside the combined catch-all account for \qty{94.1}{\percent} and \qty{93.7}{\percent} of the respective flag sets. These measured proportions establish recurring forms among detector outputs. API-associated risk remains unmeasured because the study lacks resolved call targets and denominators for all uses of each form.

The dominant categories provide useful strata for an independent corpus audit. Sampling flagged and unflagged uses within each stratum would test transfer beyond the held-out projects and estimate class-specific errors in the corpus. Resolving call targets and counting all relevant API uses would then permit exposure-normalised comparisons. These steps are prerequisites for claims about associations between particular APIs and antipattern flags.

The same strata also support controlled follow-up experiments. A same-task deterministic baseline could test explicit rules for recurring forms, and a hybrid baseline could route unresolved or context-dependent cases to an LLM. A context-ablation study could measure the effect of schema and call-resolution evidence on occurrence agreement. Finally, documentation or developer studies could test whether guidance and localised warnings change comprehension or query construction. These are proposed studies. The present measurements establish flag patterns and provide no evidence about their causes, design quality, or developer impact.

The operational scope could be tested against classes drawn from broader and more specialised SQL-antipattern taxonomies \nobreakcite{alshemaimri2021survey,10.1007/978-3-031-09070-7_26,10.1007/978-3-031-35311-6_51,factor2014sql,karwin2026more}. Such an experiment would define each added class, create project-disjoint reference annotations, and report occurrence-level agreement under the same matching rule. A separate model comparison could run the fixed task with smaller or self-hosted models and measure agreement, runtime, memory use, and direct cost. These measurements would estimate how agreement and resource use vary across the tested model and hosting configurations.

Transfer to another query builder requires a separate corpus and annotations specific to that representation. Repeating the held-out and corpus procedures on that material would test which operational definitions and source-fragment categories transfer. The preserved \num{15931} jOOQ flags also permit a separate detector-informed audit for recurring database-design patterns outside the two query classes analysed here. Sampling and adjudicating those flags could establish an audited description of any newly proposed categories before using them as rule candidates.
