\begin{abstract}
SQL antipatterns are recurring database design and query mistakes that can degrade maintainability, correctness, and performance. Detecting them in application code is difficult when SQL statements are constructed dynamically through domain-specific libraries such as \jooq. We study whether large language models can support line-level localisation of SQL antipatterns in \jooq-based Java code and use the resulting detector to investigate how these antipatterns occur in open-source projects. We construct a manually annotated dataset of 1,562 occurrences from 61 GitHub projects and evaluate detection as a multi-label, multi-occurrence localisation task using line-span Intersection over Union, precision, recall, and F1-score. On the held-out test set, the selected detector achieves a weighted F1-score of 0.88 against the original human ground truth. We then apply it to 602 projects containing 17,450 relevant files and flag 15,931 occurrences of seven SQL antipatterns. Implicit Columns and ID Required appear in 535 and 523 projects, respectively. Exploratory co-detection analysis reports unadjusted project- and file-level patterns, while API-level analysis shows that a small set of \jooq convenience methods is associated with many query-antipattern occurrences. The findings provide bounded empirical evidence about detected SQL antipatterns in \jooq projects and show where LLM-based localisation can complement, but not replace, deterministic static analysis of dynamic database access code.
\keywords{Empirical software engineering \and SQL antipatterns \and Static analysis \and Large language models \and Mining software repositories \and \jooq}
\end{abstract}

\section{Introduction}
\label{sec:introduction}

SQL remains one of the most widely used languages in software systems, yet recurring database design and query mistakes continue to appear in production code. These recurring mistakes are commonly described as SQL antipatterns: familiar but flawed solutions to database problems \cite{karwin2023sql}. Prior work has reported SQL antipatterns in both open-source and industrial systems and has linked them to maintainability and quality concerns \cite{muse2020prevalence,sharma2018smelly,lyu2019quantifying,DBLP:conf/sigmod/DintyalaNA20}. Despite this evidence, tool support remains uneven, especially when database access code does not contain plain SQL strings.

This paper focuses on \jooq, a Java library for constructing SQL statements through a type-safe domain-specific language. \jooq improves integration between Java and relational databases, but it also complicates static analysis: SQL statements can be built through fluent APIs, generated schema classes, intermediate Java variables, and conditional control flow. Traditional approaches that first extract SQL statements and then parse them can therefore miss behaviours that are visible in the source code but hard to reconstruct as complete SQL statements \cite{nagy2017static,meurice2016static}. Large language models (LLMs) offer a possible alternative because they can reason over source-level context without requiring a complete language-specific extractor for every dynamic query pattern.

Rather than treating LLM output as a file-level classification only, we evaluate SQL-antipattern detection as a localisation task: a detector must identify both the antipattern type and the line span where the occurrence appears. This makes the measurement correspond to the warning sites later counted in repositories. It also makes the output more relevant to maintenance: developers can inspect a concrete projection, predicate, or generated-schema declaration, and tool builders can route stable API patterns to deterministic rules while reserving semantic cases for contextual analysis.

The novelty of the study lies in its linked measurement design, rather than in the use of an LLM alone. SQLInspect-style approaches extract SQL from host-language code before applying specialised rules, while API- or abstract-syntax-tree-based rules encode stable source patterns directly \cite{nagy2017static,nagy2018sqlinspect,muse2020prevalence}. Recent LLM code-smell studies commonly evaluate recognition or classification, and other work tests LLMs on conventional static-analysis tasks \cite{de2025effectiveness,sadik2025benchmarking,alomari2026smelly,su2026static}. Our study instead evaluates multi-label, multi-occurrence line-span localisation in dynamic \jooq code on a project-disjoint held-out set and then carries the measured class-specific limitations into repository-level prevalence, exploratory co-detection, and API-association findings. We do not claim that this design supersedes deterministic rules or independently validates every population output.

The study has two connected goals. First, we evaluate whether LLMs can localise SQL antipatterns in \jooq-based Java code with sufficient accuracy to serve as a research instrument. Second, we use the resulting detector to analyse the prevalence, co-occurrence, and API-level manifestations of SQL antipatterns across a large set of open-source \jooq projects.

We address the following research questions:

\begin{description}
    \item[RQ1:] How accurately can LLMs localise SQL antipattern occurrences in \jooq-based Java code?
    \item[RQ2:] How prevalent are SQL antipatterns in open-source \jooq projects?
    \item[RQ3:] Which SQL antipatterns co-occur across projects and files?
    \item[RQ4:] Which \jooq API methods are most frequently associated with query antipattern occurrences?
\end{description}

We separate RQ3 from RQ4 because they capture different empirical dimensions of the same phenomenon. RQ3 studies project- and file-level relationships among antipatterns, whereas RQ4 studies concrete source-level API patterns associated with query antipattern occurrences.

The paper makes the following contributions:

\begin{itemize}
    \item a manually annotated dataset of 1,562 SQL-antipattern occurrences in 61 \jooq projects;
    \item an evaluation of LLM-based SQL-antipattern detection as a multi-label, multi-occurrence localisation task;
    \item bounded detector-output measurements for seven SQL antipatterns across 602 open-source \jooq projects;
    \item exploratory co-detection and \jooq API-association evidence that can inform documentation, developer guidance, and future static-analysis tools.
\end{itemize}

\section{Background and Related Work}
\label{sec:background}

\subsection{SQL Antipattern Detection}
\label{sec:sql-antipattern-detection}

SQL antipatterns describe recurring database design, query, and application-development mistakes \cite{karwin2023sql}. Prior empirical work has shown that such antipatterns are present in real systems and can persist for long periods \cite{muse2020prevalence}. Sharma et al. studied SQL smells in database-centric applications, while Muse et al. analysed the prevalence of SQL antipatterns using SQLInspect, a static-analysis tool that extracts SQL statements from Java code before detecting selected antipatterns \cite{sharma2018smelly,muse2020prevalence,nagy2017static,nagy2018sqlinspect}.

SQL antipatterns vary in the evidence needed for detection. Some are visible in a single query, such as selecting every column when only a subset is required. Others concern schema design, including generic surrogate-key naming, missing foreign keys, inappropriate use of floating-point types, encoded value domains, or ambiguous use of nullability. Still others depend on developer intent: a \texttt{LIKE} predicate may implement legitimate prefix search or may be an inefficient substitute for full-text search. Consequently, a detector must do more than find keywords. It must define which source representation is in scope, translate database-level concepts into observable source-level rules, and distinguish syntactic signals from decisions requiring domain context.

Prior work also differs in the unit being measured. Schema-oriented techniques can inspect catalogues or DDL and reason about constraints independently of application execution. Query-smell studies may count affected statements, files, occurrences, or projects, each answering a different question. Project presence captures dissemination but treats one and hundreds of occurrences alike; occurrence counts capture intensity but correlate with project size; statement-normalised rates depend on how statements are extracted or approximated. Prevalence values therefore cannot be compared safely without examining their denominator and source representation.

An antipattern is also not automatically a defect. It denotes a recurring solution with recognised liabilities, but local workload, compatibility, or domain constraints can justify the trade-off. Static tools rarely possess enough execution evidence to decide whether every instance is harmful. We annotate conformance to explicit operational definitions rather than observed production failures. Detector precision therefore measures agreement with that codebook, not the proportion of warnings that developers must change.

This query-extraction architecture is a natural fit for embedded SQL strings, but it creates a dependency on the completeness of the extractor. Meurice et al. report query-extraction precision of at least 0.879 and recall of at least 0.715 across evaluated systems \cite{meurice2016static}; Nagy et al. and Muse et al. consequently treat extraction quality as a limiting factor for downstream antipattern detection \cite{nagy2017static,muse2020prevalence}. This limitation is especially relevant for \jooq because source code can express database behaviour through generated schema classes, fluent API calls, and host-language control flow rather than directly parseable SQL strings.

Extraction and source-level analysis should not be treated as mutually exclusive. Reconstructing a query enables mature SQL parsers and deterministic rules, produces repeatable warnings, and may expose relationships that are obscured by a fluent call chain. Direct source analysis avoids requiring a complete reconstruction step and can incorporate Java-level context, generated-schema metadata, and library semantics. The trade-off is that an LLM detector has weaker determinism, higher runtime and monetary cost, and less transparent failure modes. The appropriate comparison is therefore not simply which technique obtains a higher score, because the evaluated representations, supported antipatterns, and units of localisation differ. We use extraction-based work to establish the problem and comparison boundaries, not as a directly comparable baseline.

Rule-based and learned approaches incur different maintenance costs. A parser and rule set must be updated when a host library introduces a construction pattern, but its accepted language and warning condition remain inspectable. A general LLM can recognise unenumerated forms without a dedicated parser, yet behaviour may change with model snapshots or provider infrastructure. That flexibility is useful for empirical mining only when validation is reported at the same granularity as later measurements. We consequently treat the LLM as a versioned measurement instrument and retain deterministic post-processing for schema validation, line matching, and aggregation.

Recent LLM-based smell and vulnerability detectors provide a second point of comparison. De et al. evaluate LLMs for PL/SQL smell detection, including a smell corresponding to the \texttt{SELECT *} subset of Implicit Columns \cite{de2025effectiveness}. Other studies evaluate LLMs for broader code-smell or vulnerability detection tasks \cite{sadik2025benchmarking,tamberg_suurte_2024,blaauwendraad2025evaluating}. These studies show that LLMs can be useful for code-quality detection, but most reported tasks are classification-oriented. Our study differs by evaluating SQL-antipattern detection as a line-span localisation task in Java source code using \jooq.

The relevant literature therefore supplies complementary baselines rather than one equivalent predecessor. SQL-smell mining motivates the target phenomena and prevalence questions; extraction research identifies a coverage bottleneck; code-smell LLM work motivates semantic source analysis; and localisation research motivates actionable output. None alone validates occurrence counts for dynamic \jooq code. We use each body of work for the part of the design it can support and avoid combining their reported metrics as if they shared labels or evaluation units.

\subsection{\jooq and Dynamic Database Access Code}
\label{sec:jooq-background}

\jooq represents SQL concepts as Java API calls and generated schema classes. This design helps developers construct type-safe queries, but it also means that antipatterns may be expressed through combinations of generated code, fluent method calls, and raw SQL fragments. For example, blind projections related to the Implicit Columns antipattern can arise from convenience methods that fetch all fields from a table, not only from explicit \texttt{SELECT *} strings. The \jooq documentation discourages blind projections when redundant data should be avoided \cite{jooq2025select}, yet such calls are among the most convenient ways to retrieve generated records.

The presence of generated schema classes is also important. Some antipatterns are visible in DDL-like generated code, such as generic primary keys or missing constraints. Others appear in DML/DQL query construction code. A detector for \jooq therefore needs to inspect both generated classes and hand-written database access code, while respecting that the two file categories expose different antipattern families.

This split has methodological consequences. Generated table classes provide a regular representation of columns, data types, defaults, and keys, but the representation reflects what the code generator could observe and what a project committed to version control. Hand-written query files are more heterogeneous: fluent calls can span methods, use intermediate variables, mix generated fields with raw SQL, and place selection and execution far apart. A single generic prompt would either expose irrelevant schema antipatterns to query files or ask the model to infer unavailable query behaviour from generated classes. We therefore treat file type as part of the detector's operational context and evaluate the combined output at the occurrence level.

API-specific rules remain a plausible alternative for several frequent cases. Calls such as \texttt{selectFrom(TABLE)} or \texttt{select().from(TABLE)} can often be recognised without an LLM, and a production tool should prefer deterministic checks where their semantics are sufficient. The harder cases motivate the broader detector: aliases and intermediate expressions obscure the final projection; nullable defaults require interpreting generated column declarations; potential foreign-key omissions require relating a column to available keys; and wildcard predicates require distinguishing search intent. Our evaluation consequently measures whether one source-level instrument can cover a heterogeneous family, not whether every detected occurrence intrinsically requires machine learning.

\subsection{LLMs for Code Analysis and Localisation}
\label{sec:llm-localisation}

Recent work has applied machine learning and LLMs to code translation, code smell detection, defect prediction, and other software engineering tasks \cite{DBLP:journals/ese/FontanaMZM16,de2025effectiveness,sadik2025benchmarking}. For the present study, the key methodological distinction is localisation. A detector that returns only a file-level label is less actionable than one that identifies the affected line span. We therefore evaluate LLM outputs using line-span overlap and classification metrics, aligning the task more closely with localised defect prediction and warning generation than with binary file classification.

LLM code-smell work establishes that source-level semantic cues can be useful, but it also narrows the available novelty claim. De et al. evaluate LLMs for PL/SQL smells, including a smell related to the \texttt{SELECT *} subset of Implicit Columns \cite{de2025effectiveness}. Alomari et al. compare in-context learning with fine-tuning for code-smell detection and explicitly study performance, generalisation, data, and computational trade-offs \cite{alomari2026smelly}. Su and McMillan test whether code LLMs perform call-graph, AST, and data-flow tasks and find that competence on programming tasks should not be equated automatically with conventional static-analysis ability \cite{su2026static}. These studies mean that neither generic code understanding nor code-smell classification is itself a sufficient research gap.

Localisation changes both the output and the evaluation problem. A file can contain multiple occurrences of one antipattern and several antipattern types. Predictions may overlap the correct source region without matching its exact boundaries, and several predictions may compete for one reference occurrence. File-level accuracy or binary confusion matrices cannot represent these cases. Line-level defect prediction offers a relevant methodological analogy because it evaluates actionable source regions, but defect-proneness localisation and explicit antipattern-occurrence localisation have different labels and evidence requirements. Our use of span overlap and one-to-one assignment therefore operationalises warning localisation for this study rather than importing a model-specific defect-prediction metric.

The remaining gap is a linked empirical question: whether a source-context LLM can be validated transparently enough to support repository mining where deterministic extraction is incomplete, and what bounded evidence that instrument produces about \jooq projects. Addressing only detector performance would yield another model comparison; reporting prevalence without validating the instrument would make the large-scale counts difficult to trust. The study design connects the two and keeps their uncertainties visible.

This positioning limits the contribution claim. We do not establish that LLMs internally construct ASTs, data-flow graphs, or executable SQL, and we do not compare fine-tuning with prompting. We test observable warning performance under a fixed source representation. Nor does line-span output alone demonstrate developer usefulness. The contribution is the empirical linkage of an operationalised heterogeneous task, occurrence-level validation, and a repository study that carries measured detector limitations into its conclusions.

\section{Study Design}
\label{sec:study-design}

\subsection{Repository Mining and Dataset Construction}
\label{sec:repository-mining}

We mined GitHub repositories for Java projects that use \jooq and store generated \jooq classes in version control. The generated classes were required because several database design antipatterns can only be detected from schema representations; compiling arbitrary GitHub projects to generate those classes would introduce substantial build and dependency failures.

A project qualified when it contained Java source using \jooq for database access, committed generated classes representing its schema, and contained non-generated Java files referencing \jooq or generated classes. Reconstructing generated classes for arbitrary repositories would have required project-specific Java versions, databases, private dependencies, and code-generator configurations. The restriction makes both query and schema source available for analysis, but narrows the target population to projects that commit derived artifacts.

The mining process used the GitHub Code Search API \cite{githubSearchApi} to search Maven and Gradle manifest files for \jooq dependencies. On 10 January 2026, the search identified 3,829 projects declaring a \jooq dependency. Filtering for repositories with generated \jooq classes reduced this set to 802 projects. Filtering again for non-generated Java files referencing \jooq reduced the set to 645 projects. Manual, LLM-assisted duplicate and fork review removed 42 projects, resulting in 603 projects. A later duplicate removal yielded the final analysis set of 602 projects.

We searched Maven XML/POM and Gradle Groovy/Kotlin manifest syntax rather than Java imports. Import searches can be saturated by files from a few large repositories, while manifest matches identify dependency declarations more directly. Query variants covered the core artifact, code-generation and metadata artifacts, extensions, and common plugin syntax; the exact strings are included in the supplementary material. GitHub limits a code-search query to 1,000 results, so specific variants reduced overlap. Where a query still exceeded the limit, the retrieved set reflected GitHub's most recently indexed results.

The duplicate review used repository file trees to generate possible clone groups with LLM assistance, followed by manual verification of every omission. The 42 removed repositories included tutorial-copy clusters and \jooq derivatives. A duplicated project found during preparation of the full analysis was removed before prevalence statistics were calculated. These stages are reported separately so the change from 603 sampled candidates to 602 analysed projects is auditable.

This mining strategy is intentionally conservative. It favours projects where source-level analysis of both query code and generated schema code is possible. Its main limitation is incompleteness: the GitHub Code Search API limits each query to 1,000 results, and projects using other build tools or not committing generated \jooq classes are outside the final population.

To construct the annotation sample, we defined a relevant database-access file as either a useful generated \jooq class or a non-generated Java file referencing \jooq/generated types. Known irrelevant generated paths, including records, POJOs, and external system schemas, were excluded. Head-tail breaks over relevant-file counts produced boundaries of 31 and 94 files: 467 projects were small, 100 medium, and 36 large. Using pseudo-random seed 123456, we sampled 10\% from each group, selecting 47 small, ten medium, and four large projects. A later corrected file filter changed the boundaries to 29 and 91 and the class sizes to 468, 98, and 36, but preserved the distribution shape. We retained the original 61-project sample to avoid selecting evaluation data retrospectively.

For project file count $x$ and set $S$, the first head-tail boundary is the mean $\mu_1=|S|^{-1}\sum_{x\in S}x$. The second is the mean $\mu_2$ of projects above $\mu_1$. Projects at or below $\mu_1$ are small, those between $\mu_1$ and $\mu_2$ medium, and those above $\mu_2$ large. Sampling the same proportion within each class preserves rare large projects without making them dominate the manual workload. It does not make the sample representative of all possible \jooq systems; it makes size coverage explicit within the mined frame.

This process is a reproducible selection funnel, not a census. Projects using other build systems, projects hidden by the result cap, closed-source systems, and repositories generating schema classes only during builds are absent. Accordingly, later prevalence estimates describe this corpus of open-source GitHub \jooq projects.

\subsection{Operational Definitions}
\label{sec:operational-definitions}

The annotation scope began with Karwin's SQL-antipattern catalogue \cite{karwin2023sql}. Nineteen antipatterns were judged observable in static \jooq source. We excluded Index Shotgun because selecting an index requires workload and execution-plan evidence; Spaghetti Query because no defensible source threshold distinguished necessary complexity from a smell; Pseudokey Neat-Freak and Diplomatic Immunity because they depend on organisational practices; and See No Evil because frameworks often handle database exceptions outside the analysed query file. Fear of the Unknown was limited to database-design evidence and query conditions whose null behaviour could be determined without tracing arbitrary Java inputs.

The annotation process covered 19 SQL antipatterns from Karwin's taxonomy \cite{karwin2023sql}. Each occurrence was recorded with project, file path, antipattern name, code fragment, line range, and reasoning. The final annotated dataset contained 1,562 occurrences. For model evaluation and large-scale analysis, we retained seven qualifying antipatterns with sufficient support across projects and occurrences: Implicit Columns, ID Required, Keyless Entry, Fear of the Unknown, 31 Flavors, Poor Man's Search Engine, and Rounding Errors. Antipatterns occurring in fewer than three projects or fewer than 25 total occurrences were excluded from later experiments to avoid drawing conclusions from sparse classes.

\emph{Implicit Columns} denotes a blind projection of every table field. It includes literal \texttt{SELECT *} and \jooq calls that fetch all generated fields or complete records, but excludes count/existence operations whose projection is not returned as application data. \emph{ID Required} denotes a synthetic primary key named only \texttt{id}, or an unnecessary surrogate where a stable, manageable natural key is represented; views are excluded. \emph{Keyless Entry} denotes a likely reference column for which a suitable target key exists but no foreign key is represented, making it more contextual than a suffix match.

\emph{Fear of the Unknown} includes special defaults used for missingness, nullable declarations for fields that always receive non-null values, and query predicates whose treatment of a nullable database field is demonstrably wrong; generic Java nullability is outside scope. \emph{31 Flavors} covers enumerations or restrictive checks used instead of lookup tables, excluding emptiness and range checks. \emph{Poor Man's Search Engine} covers \texttt{LIKE}, case-insensitive \texttt{LIKE}, or regular expressions used for full-text-style search; legitimate prefix searches are excluded. \emph{Rounding Errors} covers fixed-precision domain values represented by floating-point rather than decimal/numeric columns.

These rules adapt database-level descriptions to observable \jooq constructs. For example, \texttt{selectFrom(TABLE)} expresses the blind projection of \texttt{SELECT *} without containing a wildcard string. Conversely, the presence of a method capable of expressing an antipattern is not sufficient: the code must meet the applicable contextual rule and exclusions. The full decision trees remain in supplementary material, while the main text records the boundaries needed to interpret the labels.

\subsection{Annotation and Adjudication}
\label{sec:ground-truth}

One annotator with prior \jooq and SQL-antipattern experience reviewed the 61 projects. Each occurrence was stored in a spreadsheet and exported to CSV with its type, repository, repository-relative file, inclusive start and end lines, code fragment, and rationale. The heterogeneous repositories were not executed because many required unavailable environments or dependencies and the target task was static analysis. Every sampled project contained an occurrence; the final dataset contained 1,562 occurrences of 19 antipatterns, including 795 Implicit Columns and 259 ID Required occurrences.

The annotation codebook was developed iteratively as decision trees. When review exposed a new variant or non-antipattern edge case, the corresponding tree was updated and earlier files potentially affected by the change were re-reviewed. This reduced reliance on memory or intuition, but it did not create independent expert consensus.

The ground truth was created by a single annotator. To assess internal consistency, a subset of 128 files was re-annotated after a 30-day washout period. The resulting Cohen's Kappa was 0.834, indicating high consistency over time. This value does not replace inter-annotator agreement; it is a consistency check rather than evidence of independent expert consensus.

The 128-file subset combined a seeded 10\% sample of files containing occurrences with an equal number of randomly sampled files without occurrences. Re-annotations matched only when the label and inclusive line span were identical. A 16-by-16 confusion matrix represented 15 observed antipatterns plus background. The resulting $\kappa=0.834$ therefore measures temporal consistency under exact localisation, not merely agreement that a file is positive.

No independent adjudicator was available. Later qualitative review of detector disagreements identified missed human occurrences and incorrect reference labels or spans, producing a corrected ground-truth variant. Because the detector selected which cases received extra scrutiny, the corrected variant is biased in its favour and cannot reveal cases missed by both sources. We retain the original labels as primary and use corrected results only as an optimistic sensitivity analysis.

\subsection{Data Partitioning}
\label{sec:data-partitioning}

The 61 annotated projects were assigned to training, validation, and test splits as whole projects rather than splitting files from the same project across different subsets. This avoids prompt development and evaluation sharing project-specific conventions. The split used a Monte Carlo seed search over one million candidate seeds to balance antipattern counts across a 34/33/33 project split. The selected seed was 767573.

The training set supported iterative prompt development and supplied few-shot examples, the validation set compared model/prompt combinations, and the test set was reserved for the final detector. The balancing objective and complete split construction are reported in Online Resource~1. The selected split had score 0.52. Its test supports were 270 Implicit Columns, 105 ID Required, 36 Keyless Entry, 36 Fear of the Unknown, 39 31 Flavors, 21 Poor Man's Search Engine, and 16 Rounding Errors occurrences. These denominators are reported with the detector metrics because class-specific estimates based on 16 cases carry visibly different sampling uncertainty from those based on 270. The data-dependent balancing is not a simple random partition, but the held-out projects remained unused during detector selection.

\subsection{Model and Prompt Selection}
\label{sec:model-prompt-selection}

We evaluated four contemporary models selected for architectural diversity, performance, repeatability, and structured-output support: OpenAI GPT-5.2, Z.ai GLM-5, Anthropic Claude Opus 4.5 with reasoning disabled, and OpenAI gpt-oss-120B \cite{gpt52,DBLP:journals/corr/abs-2602-15763,opus45Card,DBLP:journals/corr/abs-2508-10925}. Structured outputs were required so responses could be validated against a schema rather than parsed from free text \cite{structuredOutputs}. The experiments were executed through OpenRouter as a unified provider gateway, with model fallbacks disabled \cite{openRouter2026homepage}.

The models represented closed reasoning, open reasoning, closed non-reasoning, and open-weight configurations. Requests were pinned to the requested model, and a local retry policy handled failed, empty, or schema-invalid responses. Provider-specific parameters, retry behaviour, and operational measurements are reported in Online Resource~1. The experiment therefore compares deployable configurations on one task rather than isolating model architecture as the sole variable.

The prompt design separated generated-schema files from hand-written query files. Schema prompts targeted database-design antipatterns and received additional constraint context needed for cases such as Keyless Entry. Query prompts targeted DML/DQL antipatterns in code interacting directly with \jooq. Each input line was prefixed with its line number to reduce localisation errors. The final detector used Claude Opus 4.5 with reasoning disabled, temperature set to 0.0, and zero-shot prompts. This configuration was selected because the evaluated prompt-engineering variants did not consistently improve detection performance and increased cost or runtime.

Four strategies were compared on the validation set: zero-shot instructions, few-shot prompts, chain-of-thought prompting, and tree-of-thought prompting. Few-shot examples came primarily from training projects; synthetic examples covered variants absent from that set. Each combination analysed the same 20 validation projects and 823 relevant files. Accuracy, cost, runtime, and retry counts were recorded. The comparison was a single-run descriptive experiment: we did not test statistical significance or estimate run-to-run variance.

Every prompt provided a numbered source file, the applicable antipattern definitions, instructions to return an empty occurrence list for a negative file, and a schema restricting each occurrence's label and inclusive bounds. Generated-schema prompts also received relevant key declarations for relational decisions. The response rationale was retained for qualitative analysis but did not enter the quantitative matching rule. Full prompt text and sample inputs are supplementary so the main manuscript can explain the protocol without relying on an inaccessible implementation detail.

Under zero-shot prompting, GPT-5.2, GLM-5, and Claude Opus 4.5 each achieved weighted F1 of 0.88 on validation, while gpt-oss-120B achieved 0.83. More elaborate prompts did not improve performance consistently and increased operational cost or runtime. We therefore selected the zero-shot Claude Opus 4.5 configuration, which combined tied baseline accuracy, strong Keyless Entry precision, valid outputs, and the shortest runtime. Complete cost, runtime, retry, and prompt-strategy results are reported in Online Resource~1. This is a task-specific engineering choice, not a general ranking of the models or prompting methods.

\subsection{Evaluation Protocol}
\label{sec:detector-metrics}

We evaluate detection as a multi-label, multi-occurrence localisation task. Each prediction contains an antipattern type and inclusive line range. Given predicted line set $S_p$ and ground-truth set $S_g$, line-span Intersection over Union (IoU) is

\begin{equation}
\mathrm{IoU}(S_p,S_g) = \frac{|S_p \cap S_g|}{|S_p \cup S_g|}.
\end{equation}

A prediction is a true positive when its antipattern type matches and $\mathrm{IoU}\geq0.5$. A wrong-label or below-threshold prediction is a false positive; an unmatched reference occurrence is a false negative. The threshold tolerates small span-boundary differences while requiring at least half of the combined source region to overlap. It is an operational choice for this study rather than a universal warning-localisation threshold.

Matching is one-to-one. When several predictions overlap a single same-label reference, Non-Maximum Suppression retains the prediction with the highest overlap as the true positive and counts the others as false positives. This prevents duplicate warnings from inflating recall. We calculate precision, recall, and F1 for each antipattern and report weighted totals using reference support. Absolute TP, FP, FN, and test support accompany the ratios so readers can reproduce the metrics and see class imbalance.

Specifically, $P=\mathrm{TP}/(\mathrm{TP}+\mathrm{FP})$, $R=\mathrm{TP}/(\mathrm{TP}+\mathrm{FN})$, and $F_1=2PR/(P+R)$. The support-weighted mean is $\sum_a N_a x_a/\sum_a N_a$, where $N_a=\mathrm{TP}_a+\mathrm{FN}_a$. We also report micro totals. Weighted averaging preserves per-class metrics while giving common classes greater influence; micro averaging pools decisions first. Neither replaces inspection of individual classes.

The final held-out run used Claude Opus 4.5, reasoning disabled, temperature 0.0, zero-shot schema/query prompts, structured output, and disabled provider fallbacks. It analysed 20 test projects containing 502 relevant files in 386 seconds at a cost of USD 14.34. The untouched human annotation is the primary reference. The corrected ground truth and a classification-only evaluation are secondary views: the former estimates the effect of known reference errors under an optimistic correction process, and the latter removes the requirement to localise multiple source spans. Neither quantifies model nondeterminism because the test call set was executed once.

\subsection{Large-Scale Statistical Analysis}
\label{sec:large-scale-method}

We applied the detector to all 602 projects in the final dataset. The analysis covered 17,450 relevant files. For each antipattern, we measured occurrence count, number of containing projects, occurrences per project, occurrences per containing project, and occurrences per 100 \jooq statements. Because statically counting executed SQL statements in dynamic \jooq code is unreliable, the final metric uses references to \jooq API methods that execute SQL statements as a proxy. This proxy supports within-study comparison but should not be directly equated with statement-density metrics from plain-SQL studies.

The statement proxy counts source references to \jooq API methods that execute SQL. Loops, branches, reuse, and dynamic construction can make runtime statement counts substantially different, so the rate is descriptive within this corpus and is not directly comparable to plain-SQL statement-density measures. Full-run cost and elapsed time are reported in Online Resource~1.

The large-scale stage reused the detector without further prompt or model selection after observing test performance. Generated and non-generated files followed the same routing rules used during evaluation, and structured occurrences retained repository, path, antipattern, span, code fragment, and rationale fields for later aggregation. This ordering is important: adapting the detector to patterns seen in the 602-project output would entangle instrument development with the population being measured. Qualitative interpretation was performed after counts had been produced and did not relabel the corpus automatically.

Repository inclusion, file discovery, detector execution, and statistical aggregation are separate stages in the artifact. This separation permits a replication to substitute a newer model while retaining the corpus and metrics, or to rerun mining while retaining the detector configuration. It also exposes where a changed result originates. Reproducibility remains conditional on external repositories and model endpoints, but the procedural inputs are versioned rather than reconstructed from narrative alone.

To analyse co-occurrence, we computed Jaccard indices, conditional probabilities, and Spearman correlations at both project and file levels. To analyse API associations, we manually categorised the \jooq API methods most frequently associated with query antipattern occurrences.

For sets $A$ and $B$ of projects or files containing two antipatterns, Jaccard similarity is $|A\cap B|/|A\cup B|$, while directional conditional probability is $P(B\mid A)=|A\cap B|/|A|$. Spearman's $\rho$ uses ranked occurrence counts over the union of units containing either antipattern, including correction for tied ranks. Jaccard measures shared presence, conditional probability shows asymmetric containment, and Spearman measures monotonic association in intensity. None establishes causality, and high marginal prevalence can inflate the first two.

API association analysis was limited to Implicit Columns and Poor Man's Search Engine. Database-design cases mainly reflect generated schema output, while only 16 Fear of the Unknown detections (1.3\%) appeared in query code. We iteratively matched occurrence snippets to concrete \jooq or raw-SQL patterns until at least 98\% received a label, retaining the residual as other/uncategorised. These labels describe where detections manifest, not whether an API method causes an antipattern.

All aggregation uses static repository snapshots and gives each repository or file one row at the corresponding analysis level. Project-level presence is binary for Jaccard and conditional probability, whereas Spearman uses the detected occurrence count. File-level analysis follows the same distinction. We report selected patterns in the main text and preserve complete matrices in Online Resource~1. The analysis did not adjust occurrence-count relationships for repository size, and no separate manual audit validated detector outputs from the 602-project population. The matrices are therefore exploratory co-detection summaries, not inferential or size-controlled associations.

The detector achieved weighted precision, recall, and F1 of 0.88. Across all classes it matched 460 of 523 reference occurrences and produced 76 unmatched predictions. The hardest antipatterns were Keyless Entry and Fear of the Unknown. Both require contextual judgement about schema relationships, business concepts, or the meaning of default and nullable values. For example, Keyless Entry requires deciding whether an apparent identifier column should refer to another table and whether an appropriate key exists. Fear of the Unknown requires distinguishing genuinely nullable values from special defaults or nullable declarations that are semantically non-nullable. These cases expose the main limitation of file-local prompting: some decisions depend on project conventions and domain semantics that may not be present in the analysed file.

The two hard classes failed differently. Keyless Entry recall was 0.97, but its 30 false positives reduced precision to 0.54. The detector frequently inferred a relationship from column naming or domain similarity that the annotation rules did not consider sufficiently supported. Fear of the Unknown had both low precision (0.44) and recall (0.53), reflecting ambiguity in whether a default has a legitimate business meaning and whether a nullable declaration can in practice receive null. These are not simply boundary-localisation errors; many require evidence outside the presented file. Adding more verbose instructions is unlikely to recover absent project semantics.

Manual error inspection identified recurring sources of disagreement. Audit columns and technical identifiers were sometimes interpreted as domain references; columns with names suggesting a relationship did not always have a suitable target; and generated defaults could represent framework conventions rather than missing-value sentinels. For query antipatterns, the model sometimes inferred wildcard intent from a method name without seeing caller-provided values, or omitted a case when string construction was separated from the predicate. These patterns explain why file-local semantic flexibility improves coverage but cannot substitute for explicit project retrieval.

The strongest performance appeared for antipatterns with more local syntactic or API-level signals, such as Implicit Columns and 31 Flavors. This pattern supports the use of LLMs as a flexible detector for source-level antipatterns, but it also suggests that future improvements should focus on retrieval or static pre-analysis for context-dependent cases rather than simply adding more prompt instructions.

Implicit Columns combined precision 0.98 and recall 0.94 across 270 test occurrences, indicating that the model usually recognised both explicit and API-mediated blind projections. 31 Flavors achieved F1 0.97, although its support was only 39. Rounding Errors produced no false positives and three false negatives among 16 occurrences. The latter perfect precision should therefore be read with its denominator: a few additional errors would change it substantially. Poor Man's Search Engine showed the opposite practical concern, missing eight of 21 reference cases, often where wildcard intent was indirect.

\paragraph{Ground-truth sensitivity analysis}
Reviewing detector disagreements corrected known omissions or mistakes in the reference data. Against that revised variant, weighted precision increased from 0.88 to 0.96, recall from 0.88 to 0.91, and F1 from 0.88 to 0.93. The largest changes occurred for context-sensitive schema classes: Keyless Entry F1 rose from 0.69 to 0.86 and Fear of the Unknown from 0.48 to 0.82. This shows that reference uncertainty materially affects class-level conclusions. It does not provide a less biased performance estimate, because detector-disagreed cases received disproportionate review and jointly missed occurrences remain unknown. We consequently retain 0.88 as the primary result and use 0.93 only to show the direction and possible magnitude of known annotation error.

Classification mode achieved a similar weighted F1-score: 0.88 against the original ground truth and 0.94 against the corrected ground truth. It is nevertheless less useful as a static-analysis output because it cannot distinguish multiple occurrences in the same file or identify the exact code range that should be inspected. We therefore treat classification as a secondary robustness check and use the localisation mode as the primary instrument for the large-scale study.

This comparison suggests that requiring line spans did not reduce the aggregate weighted F1 relative to classification in this experiment. It should not be interpreted as equivalence between tasks: classification collapses multiple same-type occurrences and cannot penalise imprecise warning locations. The localisation counts remain the appropriate evidence for a detector whose outputs are later counted as individual occurrences.

The validation-to-test transition also provides a limited check against configuration selection bias. The chosen model achieved validation weighted F1 of 0.88 under zero-shot prompting and the final localised test F1 was likewise 0.88, despite the test set containing different projects and 502 rather than 823 files. Similar aggregates do not demonstrate distributional equivalence, but the absence of a large collapse supports the decision to use the held-out detector for corpus analysis. Class-level denominators remain the more informative evidence.

Because all 523 original test occurrences contribute to the weighted estimate, its apparent two-decimal precision should not be mistaken for exact population performance. Scores for low-support classes remain especially fragile, and all model calls were single observations. We use two decimals for consistent reporting and base downstream confidence on the combination of counts, error types, and class support rather than on small differences in rounded F1.

\paragraph{Answer to RQ1}
On 523 held-out reference occurrences, the selected zero-shot Claude Opus 4.5 detector achieved weighted localisation F1 of 0.88 against the original human ground truth. Performance was strongest for locally expressed antipatterns and weakest for definitions requiring project or domain context. The result supports using the detector as a fallible large-scale research instrument, provided that prevalence findings are phrased as detected occurrences and class-specific error differences remain explicit.

\section{Discussion}
\label{sec:discussion}

\subsection{What the Findings Add}

The detector outputs suggest that the operationalised patterns are not isolated edge cases in the analysed open-source \jooq projects. Implicit Columns and ID Required are flagged in nearly nine out of ten repositories. Implicit Columns is the stronger population finding because its held-out precision and recall were both high, and many occurrences are not literal \texttt{SELECT *} strings: they arise through \jooq idioms that fetch generated records or all table fields. This supports further source-level analysis that understands API semantics rather than only extracted SQL strings.

At the same time, ubiquity under an operational definition is not equivalent to uniform harm. A broad projection may be harmless for a small stable table or deliberate when a complete generated record is required. A generic \texttt{id} key may be consistent with a project's modelling conventions even when a natural key exists. Antipattern catalogues are diagnostic heuristics: they identify decisions worth reviewing, not automatically actionable defects. The large-scale counts are therefore most useful for characterising recurring design and access patterns and prioritising further investigation.

The detector results also show why localisation matters. A file-level label can indicate that a file contains an antipattern, but it does not provide enough information for a developer to inspect or fix the occurrence. By evaluating line spans with IoU, we can distinguish models that merely recognise a file-level smell from models that identify actionable source regions. This is particularly important for multi-occurrence files where several antipatterns of the same type may appear.

Localisation also makes evaluation stricter in a productive way. A model that notices the right concept but highlights an entire class gives a reviewer more work and can merge independent occurrences. Conversely, demanding exact line equality would penalise small differences in whether a fluent call's receiver or closing line is included. The IoU gate balances these concerns, and one-to-one matching prevents repeated warnings for the same site from appearing beneficial. Future user studies should still test whether the returned spans and explanations are actionable; overlap with an annotation is only a proxy for developer utility.

\subsection{Relationship to Existing Detection Approaches}

The comparison with SQLInspect-style approaches is nuanced. SQLInspect relies on extracting SQL from Java code, and the query extractor's reported performance bounds the antipattern detector built on top of it \cite{nagy2017static,meurice2016static,muse2020prevalence}. Our LLM-based approach bypasses some extraction problems by inspecting the Java source and generated \jooq classes directly. This enables detection of blind projections expressed as \jooq convenience calls and schema-level Fear of the Unknown occurrences that are outside the DML/DQL scope of SQLInspect. At the same time, this is not a direct head-to-head comparison: the tools target different representations, antipattern subsets, and evaluation designs.

Dedicated API or AST rules would be preferable for stable high-volume forms. The API-association results show that two or three patterns cover most Implicit Columns detections, and those patterns do not require probabilistic interpretation. Deterministic checks are cheaper, easier to reproduce, and easier for developers to trust. Their limitation is coverage: aliases, intermediate query objects, raw SQL mixtures, generated-schema semantics, and context-dependent relationships require additional data flow or project modelling. A practical successor should therefore be hybrid. Rules can handle high-confidence syntactic cases, while an LLM receives only cases needing semantic context and can be evaluated under the same localisation contract.

The comparison with LLM code-smell research is equally bounded. Prior studies already demonstrate classification of code smells and compare prompting or fine-tuning \cite{de2025effectiveness,sadik2025benchmarking,alomari2026smelly}. Our evidence does not establish a generally better prompting technique: zero-shot was selected because more elaborate strategies did not consistently improve this task and were operationally expensive. The distinct contribution is the use of a held-out, occurrence-localised detector as an explicitly validated instrument for a repository study. Su and McMillan's finding that coding performance does not imply conventional static-analysis capability reinforces the need for this task-specific validation \cite{su2026static}.

The density results also require careful interpretation. Muse et al. report Implicit Columns and Fear of the Unknown as percentages of SQL statements \cite{muse2020prevalence}. Our corresponding density metric counts occurrences per 100 static \jooq statement proxies, and a single generated or fluent source construct can correspond to runtime behaviour that is hard to count statically. The larger observed rates therefore should be read primarily as evidence that \jooq exposes additional source-level manifestations, not as a direct claim that \jooq projects are categorically more prone to SQL antipatterns than plain-SQL projects.

\subsection{Implications for Practice and Research}

For practitioners, the API-association results are the most actionable. The dominant Implicit Columns associations point to convenience methods that make broad projections easy and idiomatic. The Poor Man's Search Engine associations show that methods such as \texttt{contains} and \texttt{containsIgnoreCase} can hide wildcard-based matching behind a higher-level API. Documentation and examples could therefore highlight when these methods are appropriate and when more explicit projections or full-text search mechanisms should be preferred.

For \jooq users, a useful warning should state the evidence and offer a bounded alternative rather than merely name an antipattern. An Implicit Columns warning can list the selected table and suggest explicit fields when a partial record is sufficient. A search warning can distinguish prefix matching from arbitrary substring search and point to database-specific full-text facilities. Schema warnings require more caution because generated classes are not normally edited directly; they should identify the upstream schema constraint and suppress cases representing views or intentional defaults.

For tool builders, the different class error profiles argue against one global confidence threshold. High-precision local cases can be emitted directly, while Keyless Entry and Fear of the Unknown may require retrieval of migrations, neighbouring tables, naming conventions, or developer confirmation. Suppression and baseline support are important in projects where hundreds of existing occurrences would otherwise overwhelm developers. None of these workflow features was evaluated here, so the present results establish detector feasibility and research-instrument validity rather than readiness for continuous integration.

For empirical researchers, the study shows the importance of validating the measurement instrument at the same granularity used in later counting. A file classifier cannot justify occurrence totals, and an aggregate F1 can obscure a class with many false positives. Publishing test supports, absolute counts, prompt definitions, correction provenance, and full co-detection matrices enables readers to decide which downstream findings are strongest. The present study did not manually validate a sample of the 602-project outputs, repeat LLM calls, or adjust count correlations for project size. Independent population-output annotation, repeated runs, and size-controlled analysis would therefore be the most valuable additions to a replication.

The study also suggests a staged evidence standard for LLM-assisted repository mining. First, define labels in the source representation actually analysed. Second, isolate prompt development from held-out testing at project level. Third, publish absolute occurrence-matching results rather than only aggregate accuracy. Finally, phrase mined findings according to the weakest relevant class validation. This is more demanding than treating the model as an opaque classifier, but it allows flexible analysis without hiding measurement error.

The study also reveals the limits of LLM-based static analysis. Context-dependent antipatterns remain difficult, and several false positives and false negatives were tied to domain-specific interpretations of identifiers, audit tables, default values, or business logic. These cases suggest that future detectors may need retrieval over project context, explicit schema relationship modelling, or hybrid static-analysis prefilters rather than prompting alone. A practical tool would also need workflow features not evaluated here, such as suppression handling, incremental analysis, and developer-facing explanations tested in realistic maintenance tasks.

Finally, the results should be understood as a snapshot. Model identifiers, provider routing, repository contents, and \jooq idioms change. The study preserves parameters, prompts, selection dates, and artifacts so the procedure can be repeated, but a future replication may reasonably obtain different absolute scores or corpus membership. The durable contribution is therefore the operationalised task and linked validation/mining design as much as any individual model ranking.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Construct validity}
The principal construct risk is whether the labels represent SQL antipatterns consistently in \jooq source. Several definitions adapt plain-SQL concepts to generated classes and fluent APIs, which may differ from other studies. We mitigated ambiguity with explicit inclusion/exclusion rules, decision trees, re-review after guideline changes, and publication of the codebook. A 128-file washout re-annotation obtained exact-span $\kappa=0.834$, supporting temporal consistency. It does not establish expert consensus because one annotator produced both passes. The corrected-ground-truth sensitivity analysis exposes that reference errors can materially change class scores, but is optimistic because detector disagreements triggered review. The residual boundary is that prevalence applies to these operational definitions and unknown cases missed by both human and model remain unmeasured.

The IoU threshold introduces a second construct choice. A threshold of 0.5 tolerates small boundary differences, while exact matching would answer a stricter question. We mitigate duplicate and overly broad matches with same-label one-to-one NMS and publish the formula and spans. No alternative-threshold sensitivity run was performed, so the reported scores remain conditional on 0.5. Classification results show that removing localisation does not change aggregate weighted F1, but do not validate the threshold itself.

\paragraph{Internal validity}
Prompt and model selection may overfit the validation set, and single LLM runs can vary. We separated projects across training, validation, and test sets, used whole-project assignment, fixed all sampling/splitting seeds, reserved the test set for the final configuration, constrained outputs by schema, and disabled provider fallbacks. Few-shot examples came mainly from training data, but synthetic edge cases and repeated prompt iteration may still encode researcher expectations. We performed no significance tests and no repeated-run variance analysis; model/prompt comparisons are descriptive. The held-out result reduces direct test overfitting, but does not support general claims that zero-shot prompting or Claude Opus 4.5 is superior outside this task.

\paragraph{External validity}
The corpus contains open-source GitHub Java projects that declare \jooq dependencies and commit generated classes. We mitigate selection opacity by publishing exact search terms, the dated collection point, funnel counts, duplicate categories, and size-stratified sampling. Specific manifest queries reduce but cannot eliminate losses from GitHub's 1,000-result cap. Maven/Gradle selection excludes other build systems, and committed generated classes may distinguish the corpus from enterprise practice. No sensitivity corpus using another search source was available. Claims are therefore bounded to the analysed open-source population and should not be extrapolated directly to closed-source systems, build-time-only generation, other languages, or query builders such as LINQ and SQLAlchemy.

\paragraph{Conclusion validity}
Absolute detector counts inherit class-specific precision and recall, and co-detection measures are affected by repository size and marginal prevalence. We report TP/FP/FN and test supports, present three complementary summaries at project and file levels, retain uncategorised API cases, and distinguish observation from interpretation. We do not accuracy-adjust the corpus counts because errors need not be random or stable across populations. We also performed no separate manual validation of population outputs, so the held-out class estimates may not transfer unchanged to the 602-project corpus. Keyless Entry and Fear of the Unknown counts are consequently treated as low-confidence flags rather than equivalent population estimates.

The co-detection analysis did not control for project size. Larger projects create more opportunities for every antipattern, so count correlations can arise from shared exposure even without a direct relationship. Reporting both presence and count summaries and noting marginal prevalence makes this risk visible but does not remove it. The RQ3 findings are therefore hypothesis-generating unadjusted patterns; a size-stratified analysis, partial correlation, or count model with an exposure term would be required for a size-independent claim.

Occurrences per 100 \jooq statements use static SQL-executing API references rather than runtime statements; loops and control flow can change actual execution frequency. The remaining claims are detected prevalence and descriptive API associations, not causal effects, statistically significant clusters, or direct density comparisons with plain SQL.

The study did not compute confidence intervals or hypothesis tests for model, prompt, prevalence, or co-occurrence differences. This is explicit rather than repaired post hoc with assumptions unsupported by the archived outputs. Absolute denominators and complete matrices allow future project-level bootstrap or repeated-run analyses. Until then, small metric differences and weak correlations are treated as descriptive, and substantive interpretation focuses on large, repeated patterns with clear operational meaning.

Finally, API categories were developed from observed detections rather than from a preregistered taxonomy. Achieving at least 98\% coverage and retaining an uncategorised group makes the procedure inspectable, but categories may reflect this corpus. The result supports prioritising prominent methods for further study, not a complete universal classification of \jooq APIs.

\paragraph{Reliability and reproducibility}
The experiments used commercial and gateway-hosted endpoints. Provider updates, backend routing, quantisation, caching, and transient failures can affect replications. We recorded model identifiers and parameters, disabled automatic fallbacks, used structured outputs, separated invalid-response retries, retained prompts and code, and selected point-in-time snapshots where possible. The full 602-project run also records cost and elapsed time. These mitigations improve auditability but cannot recreate provider internals or guarantee deterministic output. Replications should report both accuracy and operational behaviour and should not treat exact numerical reproduction as expected from a conventional static analyser.

\section{Conclusion}
\label{sec:conclusion}

This paper validated LLM-based localisation of SQL antipatterns in \jooq database access code and used the resulting instrument for bounded repository mining. We constructed a manually annotated dataset of 1,562 antipattern occurrences, evaluated detection as a line-span localisation task, and applied the selected detector to 602 open-source \jooq projects. Against the original held-out ground truth, the detector achieved weighted F1 of 0.88 across 523 reference occurrences. The large-scale run flagged 15,931 occurrences, with Implicit Columns and ID Required appearing in nearly 90\% of projects.

The findings show that SQL antipatterns in \jooq projects often arise through API-level constructs rather than only through explicit SQL strings. They also show that LLM-based localisation can complement traditional extraction-based static analysis for dynamic database access libraries. The strongest future opportunities are hybrid detectors that combine LLM source understanding with stronger project-context retrieval, schema modelling, and reproducibility controls.

The results remain bounded by a single annotator, class-dependent detector error, no separate population-output audit, unadjusted project-size exposure, an open-source corpus that requires committed generated classes, and a single execution of each LLM experiment. Within those boundaries, the study provides a reproducible localisation protocol and empirical baseline for future independent annotation, repeated-run evaluation, size-controlled mining, hybrid rule/LLM detectors, and developer-centred assessment of warning usefulness.
